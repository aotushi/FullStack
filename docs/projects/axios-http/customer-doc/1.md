为什么onError onReort为什么不使用插件形式引入到全局位置, 例如响应拦截器或请求拦截器中呢?

一句话总纲：拦截器的作用域是"一次物理请求"，而这两个回调的语义单位是"一次逻辑请求"——终局裁决只有编排层能做，拦截器天然做不到"恰好一次"。这正是 DESIGN §6 那句"Loading、重试、最终错误标准化和 onError 围绕一次逻辑请求编排，不依赖物理 Axios 请求次数"的落点。展开讲四层原因：

1. 拦截器看不出"这是不是终局"
   一次逻辑请求可能展开为多次物理请求，每次物理失败都会走一遍响应拦截器的 rejected 链：

retry: { retries: 2 } 的请求失败 3 次 → 拦截器被调 3 次 → 3 个 toast、3 条 Sentry，违反"整个重试循环只触发一次最终 onError"（§15.3.15）。
更糟的是误报：原请求 401 → 刷新 → 重放成功，逻辑请求其实成功了。装在拦截器里的展示逻辑会先看到那个 401 错误弹一次"登录过期"，然后页面又正常渲染出数据。
拦截器在错误经过它的那一刻，无法知道这个 503 会不会被重试救回、这个 401 会不会被重放救回。要判断就得读取 retry 配置、attempt 计数、\_\_authRetry 标记这些跨模块状态——拦截器之间产生隐式耦合。而 execute() 的 catch 位于 await retry(send) 和整条 auth 链之外，能走到那里的错误必然是终局，"每逻辑请求恰好一次"在那个位置是免费的不变量，在拦截器里是要靠状态机拼凑的目标。

1. 拦截器是管道变换器，这两个回调是终局观察者——混装会破坏管道
   现有三个拦截器都在变换数据流：envelope 改写 response.data，auth 吞掉 401 发起重放并返回新响应，request-control 组合信号。它们顺序敏感，所以 D-17 才把安装顺序死死固定。

onError/onReport 不变换任何东西，只消费终局错误产生副作用，Promise 该 reject 还是 reject。硬塞进管道有一个很硬的技术冲突：错误对象的形状。auth 拦截器靠 axios.isAxiosError(error) 和 error.response.status === 401 识别认证错误——如果它前面有个拦截器提前把错误 normalize 成了 HttpError，auth 就认不出 401，整个刷新重放机制失效。所以当前设计刻意让错误在管道内保持 AxiosError 原样流动，normalizeHttpError（还是 async 的，要读 Blob 错误体）放在管道之外的 execute catch 里做。拦截器方案要么提前变换（毁掉 auth），要么报原始错误（onError 拿到的不是稳定模型，防腐层白做）。

1. "插件形式"意味着交出管道位置，违反 D-17 的边界
   设计明文："外部不暴露 setup(axiosInstance)，也不允许调用方依赖或改变注册顺序。"插件式注册口一旦开放，项目层拿到的是触碰管道的权力：谁保证项目插件恰好装在 auth 之后？装错位置，15.x 那批时序验收全部作废；拿到实例还能绕过 HttpRequestConfig 用 Omit 屏蔽 baseURL/withCredentials 的类型防线。

回调注入则是最小权力接口：核心在正确的时机、带正确的数据调用你，你只能消费、不能改变流程和顺序。依赖方向同样干净——项目把函数递进来（项目层 → 核心），核心永不 import UI/Sentry（D-32）。插件形式表面也守这个方向，但它交出的是位置，回调交出的只是值。

1. 回调需要的上下文，拦截器根本看不见
   seam 1 给 HttpError 补的 attempts 和 elapsedMs，只有编排层拥有：重试循环在 execute 里跑，计时从 execute 开始。拦截器每次只见单次物理请求，要传这些就得在 config 上继续挂私有字段接力。连同 silent 判断、handled-auth 标记、envelope 分支、cancel 豁免——全部终局裁决逻辑搬进拦截器，等于把 execute 的 catch 原样塞到一个更差的位置（每物理请求执行一次、还要自判终局）。

为什么教程里"拦截器统一弹错"看起来可行
axios 生态大量封装确实在响应拦截器里弹全局错误——那在无重试、无刷新重放的简单封装里成立，因为那时一次物理请求就等于一次逻辑请求，拦截器恰好是终点。本项目引入重试 + 单航班刷新 + 重放后，两个单位分离了，那个方案的隐性前提消失。很多项目把教程封装搬进生产后出现的"失败弹好几个 toast""token 续期瞬间闪一下报错"，根源就在这里。

所以选型规则一句话：按物理请求工作的数据变换器（带凭证、解包、登记信号）进拦截器；按逻辑请求工作的终局观察者（展示、上报、Loading 开关）走编排层回调。envelope/auth 用拦截器、onError/onReport 用工厂注入，不是新旧或高下之分，是作用域各归其位。
